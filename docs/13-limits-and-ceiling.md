# 13 · 极限定纲：基于现实的容量 / 延迟 / 吞吐 / 并发天花板

> 本文回答两个问题：**GitLite 的物理极限在哪里（由 GitHub/Gitee/Git 对象模型决定，不可协商）**；**在这些极限内能做到的最好形态是什么**。所有数字给出推导过程，可复核。
> 定位：规划基准。每次版本规划先对照本文，不立项天花板之外的东西。

## 一、硬约束清单（不可协商的外部物理限制）

| # | 约束 | 数值 | 影响 |
|---|---|---|---|
| C1 | GitHub REST 主限流 | 5000 次/h（认证） | 所有 API 调用的总池 |
| C2 | GitHub 内容创建次级限流 | **500 次/h**（blob/tree/commit/refs 创建类） | **写吞吐的真瓶颈**（每次 flush ≈ 4 次内容创建） |
| C3 | GitHub push 次级限流 | 6 次/min/仓库 | 写突发上限 |
| C4 | Tree API 条目上限 | 递归列表 **10 万条目截断** | 全量读模型（getFiles）的文件数上限 |
| C5 | 单文件读取 | Contents API 1 MB | 单文档、单分片上限 |
| C6 | 仓库大小 | 软限 1 GB / 硬限 5 GB（Gitee 免费版 500 MB） | 总数据量上限 |
| C7 | Gitee 免费版 | 私有仓 5 个 / 仓库 500 MB / 5000 次/h | 分支模式（默认仓 1 个）已规避仓库数限制 |
| C8 | 网络 RTT | 100–1000 ms/次 | 任何远端操作的下限 |
| C9 | Git ref 单点 | 一个分支只能线性快进 | **多写者并发的结构性瓶颈** |

## 二、四维极限推演

### 2.1 容量极限

```
条目维度：C4 = 10 万 tree 条目
  L2 分片模式下每表占 ⌈行数/1000⌉ + 常数个条目 → 条目几乎不会先到顶
大小维度：C6 软限 1 GB，留 30% 给历史/索引/系统文件
  → 数据净容量 ≈ 700 MB ≈ 100 万行 × 0.7 KB
```

| 维度 | 硬极限 | 舒适区（设计目标） |
|---|---|---|
| 单表行数 | ~50 万行（500 个分片，pull 增量化之后可用） | **≤ 10 万行** |
| 全库总行数 | ~100 万行（受 C6） | **≤ 50 万行** |
| 单文档 | 1 MB（C5） | ≤ 64 KB |
| 仓库体积 | 1 GB（C6） | ≤ 500 MB |
| 表数量 | 无限（条目维度管不到） | < 100 个 |

**结论：GitLite 是"百万行封顶"的数据库。** 覆盖个人应用/小团队 95% 场景；GB 级数据是对象存储+仓库存引用的场景，不是我们的。

### 2.2 延迟极限

| 路径 | 极限 | 推导 |
|---|---|---|
| 本地读 | < 1 ms | 内存镜像直读（**已达成**） |
| 本地写返回 | < 5 ms | 镜像 + 队列落盘（**已达成**） |
| 自己的写持久化到远端 | 最快 ~10 s（单 push：C3 允许 6/min） | 突发可到分钟 6 次 |
| 可持续同步频率 | **~30 s/次** | C2：500/h ÷ 4 调用/commit ≈ 125 commit/h ≈ 29 s/commit；留 50% 余量 → 1 min 档（realtime）是安全稳态 |
| 多端可见性（零服务器） | **1 分钟级封顶** | 轮询下限受 C1/C2 约束 |
| 多端可见性（秒级） | 需引入 webhook → broker → WebSocket | **违背零服务器形态**，定位为可选付费/自建组件，永不进核心 |

### 2.3 写吞吐极限

```
稳态：C2 500 次/h 内容创建 ÷ 4 次/commit = 125 commit/h
      × 100 ops/commit（批量上限）= 12,500 ops/h ≈ 3.5 ops/s（平均）
突发：C3 6 push/min × 100 ops = 600 ops/min 瞬时
```

**结论：平均写吞吐个位数 ops/s 封顶，但批量突发无压力**——这决定了 GitLite 适合"写操作聚集、间隔宽松"的负载（表单、笔记、配置、任务），不适合持续高频写入（日志采集、传感器、消息队列）。

### 2.4 并发极限（C9 结构性）

| 写者数 | 状态 | 说明 |
|---|---|---|
| 1（多端同人） | ✅ 舒适 | 冲突罕见，字段级合并可兜底 |
| 2–5（小团队，低频写） | ⚠️ 可用 | OCC 重试 + 冲突事件；写频率越高体验越差 |
| >5 或高频并发写 | ❌ 架构性不适合 | ref 单点 CAS，重试风暴 |

读者无限扩展（各自独立本地镜像，零远端成本）。

## 三、能做到的最好形态（终局画像）

在上述极限内，GitLite 的完整形态是：

> **单用户多端 / 2–5 人小团队的全功能数据层**——具备查询（聚合/复合索引/全文索引）、事务（短+长事务分支）、安全（字段级加密）、灾备（多平台绑定 failover）、版本时间旅行（免费 MVCC 快照）。
> **对标物：个人版 Notion 的数据层、Obsidian Sync、Firebase 的个人级替代。不是 PostgreSQL。**

一个免费超越点重申：任意 commit = 全量快照，"上周三的数据"零成本回答——这是 SQLite 需要专门机制才有的能力。

## 四、永远做不到清单（立项红线）

| 场景 | 为什么做不到 |
|---|---|
| 多用户高并发 OLTP | C9 ref 单点 |
| GB 级大数据存储 | C6 仓库上限 + 全量读模型 |
| 跨仓库分布式事务 | 多 ref 无原子提交 |
| 亚秒级多端可见（零服务器） | 轮询受 C1/C2；秒级必须上 broker |
| 秒级同步却零 API 消耗 | 物理不可能 |
