# 14 · 引擎能力对标：离 SQLite 能逼近到哪（内圈天花板）

> 姊妹篇：[13-limits-and-ceiling.md](./13-limits-and-ceiling.md) 定"外圈"（平台配额约束下的容量/延迟/吞吐/并发——**规模上限**）。
> 本篇定"内圈"（作为数据库**引擎**，能力维度离 SQLite 能逼近到哪——**智能上限**）。
> 核心论点：**SQLite 的引擎智能是纯本地计算，不碰平台约束 → 原则上全部可移植。做不到的只有规模维度，而规模维度 SQLite 自己在嵌入式场景也不追求。**

## 一、能力对标矩阵（逐项判定）

| # | SQLite 能力 | 本质 | GitLite 可达性 | 依据 |
|---|---|---|---|---|
| 1 | SQL 解析 + 代价优化器 | 本地 CPU | ✅ **完全可达** | 纯计算。我们已有 filter AST，缺统计信息 + 计划器；已有 `explain` 设计（docs/08） |

| 3 | 事务原子性 + savepoint | 本地日志机制 | ✅ **已有 80%** | 单 commit 原子 ✅；savepoint = 长事务 checkpoint（v0.4 分支模式） |
| 4 | MVCC 读快照 / 时间旅行 | 版本机制 | ✅ **免费超越** | 任意 commit = 全量快照；SQLite 需要 WAL 专门机制才有的能力，`git log` 白送 |
| 5 | WAL 增量写 | 本地日志 | ✅ 本地侧**已有**（append-only 队列）；远端侧待做（脏集合增量 diff） | v0.2 第 6 项 |
| 6 | 崩溃恢复 | 本地日志重放 | ✅ **已有** | 队列重放 + 启动强制 flush（NFR-4 已验证） |
| 7 | 单写多读并发 | 本地锁/快照 | ✅ 本地可加多连接；**跨端**写并发受外圈 C9 约束 | 内圈能做，外圈管跨端 |

## 二、判定法则（以后每项新能力先过这个闸）

```
这项能力是「本地计算」还是「远端规模化」？
  ├─ 本地计算（解析/优化/索引/合并/加密/缓存策略）
  │    → 内圈：物理可达，只差工程量 → 立项候选
  └─ 远端规模化（更大/更快/更多并发写者）
       → 外圈：查 13 号文档，撞墙即放弃 → 不立项
```

按此法则，**"往 SQLite 靠近"这个方向 100% 成立**——因为嵌入式 SQLite 的本质就是"单文件、单写者、进程内、智能引擎"，GitLite 形态与之同构（单仓库、单活跃写者、进程内、智能引擎待补齐）。差距不在物理可行性，只在 v0.1 的实现完成度。

## 四、一句话定纲

> **外圈（13 号）告诉我们在哪停车：百万行、分钟级、个位数写者。**
> **内圈（本篇）告诉我们车里能装多少：SQLite 的引擎智能——优化器、范围索引、事务、快照、恢复——全部装得下，一项不缺。**
> **方向没有歪，歪的是节奏：接下来按 P1a→P1b→P1c 开工，全部是纯本地引擎能力。**
