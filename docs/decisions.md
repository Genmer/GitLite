# ADR-001 · 同步频率策略

**标题**：分钟级低频同步三档预设，启动/退出强制同步，细粒度可调

**状态**：已采纳（取代早期 v0 设计的秒级方案）

## 1. 背景

GitLite 的架构是「本地副本一线读写，远端 Git 仓库低频同步」。远端同步只承担两件事：持久化备份 + 多端共享。因此同步频率不必跟随读写频率——这是一个可以、也应该独立决策的参数。

### 平台配额硬约束（不可协商的外部条件）

| 限制项 | GitHub | Gitee |
|---|---|---|
| REST 主限流（认证） | 5000/h | 5000/h |
| 内容创建次级限流 | **80/min、500/h** | 类似 |
| Push 次级限流 | **6/min/repo** | 类似 |
| 单文件（Contents API） | 1 MB | 1 MB |

关键认知：**内容创建次级限流 500/h 是最紧的瓶颈**（每次 flush 涉及 blob/tree/commit/ref 多次内容创建调用），而非表面上的 5000/h 主限流。

### 用户需求（明确约束）

1. 「同步频率尽量低，别一直操作」
2. 档位预期为分钟级（1 / 5 / 10 分钟）
3. **启动、退出时必须立即同步一次**
4. 频率可由用户/app 自行设置

## 2. 备选方案对比

| 维度 | A. 秒级实时 | B. 固定中频 60s | **C. 分钟级三档（采纳）** | D. 纯手动 |
|---|---|---|---|---|
| 具体参数 | 3s 窗口 + 30s 轮询 | 60s 窗口 + 5min 轮询 | economy 10min / balanced 5min / realtime 1min | 无自动同步 |
| 远端调用/小时 | ~1200+ | ~70 | **8 / 30 / 130** | ≈0 |
| 距 500/h 次级限流余量 | **超出，必触发限流** | 余量约 7× | **默认档余量 60×** | 无限 |
| 多端可见性延迟 | 秒级 | 分钟内 | 分钟级（默认 10min） | 完全手动 |
| 数据安全 | 高（但限流时假象） | 高 | 高（与窗口无关，见 §4） | **低（忘记 sync 即断档）** |
| 「零操心」定位契合 | 差（需盯配额） | 中 | 好 | 差 |
| 满足用户分钟级要求 | 否 | 否 | **是** | 否 |

### 各方案否决/采纳理由

**A. 秒级实时（原 v0 设计）— 否决**
~1200 调用/h 直接撞穿内容创建次级限流 500/h，且 push 6/min 也会周期性触发。限流后 app 卡死在退避循环，体验反而最差。Git API 的配额结构决定了**轮询式秒级同步在 Git-as-Backend 架构上不可行**。秒级实时需求由事件总线（webhook → broker → WebSocket）外挂解决，不走轮询。

**B. 固定中频 60s — 否决**
虽然可用，但 ~70 调用/h 对个人低频工具仍属浪费；单一档位无法同时服务「个人工具（一天写几十条）」与「多端协作（持续读写）」两种负载画像；且不满足用户明确提出的分钟级档位预期。

**C. 分钟级三档预设 — 采纳**
默认档（economy 10min）把远端调用压到 <8/h，距所有限流线都有数量级余量；三档覆盖三类负载；强制启动/退出同步兜底正确性；细粒度参数保留自由度。

**D. 纯手动 — 不作默认，保留为特殊模式**
配额绝对可控，但违背「嵌入式零操心」定位——用户忘记 sync 则多端数据断档。保留为 `mode: 'manual'` 供批量导入、调试等场景。

## 3. 最终决策

### 三档预设

| 档位 | 写 flush 窗口 | 写批量阈值 | 读 pull 轮询 | 远端调用/h（估） | 定位 |
|---|---|---|---|---|---|
| **economy（默认）** | **10 分钟** | 100 条 | **不轮询** | < 8 | 个人工具、低频写 |
| balanced | 5 分钟 | 50 条 | 5 分钟 | ~30 | 多端协作 |
| realtime | 1 分钟 | 20 条 | 1 分钟 | ~130 | 高频协作（仍余量 4×） |

### 强制同步时机（不可关闭）

| 时机 | 行为 |
|---|---|
| **启动（connect）** | 立即 pull 一次 + flush 上次会话遗留队列 |
| **退出（进程退出 / app 切后台）** | 立即 flush 全部待提交队列 |
| push 冲突时 | 被动 pull（rebase 需要，非轮询） |

### 细粒度覆盖

```ts
sync: {
  policy: {
    timeWindowMinutes: 1 | 5 | 10 | 30,
    batchSize: 100,
    pullIntervalMinutes: 'off' | 1 | 5 | 10,
  }
}
```

## 4. 关键论证：为什么窗口拉长是安全的

这是本决策成立的核心推理：

1. **每次写操作即时持久化到 L3**（本地 `pending.json` 待提交队列）——写路径根本不依赖 flush 窗口。
2. flush 窗口只决定「**远端备份/其他端**落后本地多久」，不决定「数据是否安全」。
3. 进程崩溃/断电：本地队列仍在，下次启动的强制 flush 自动补推。
4. 因此窗口从 3s 放宽到 10min，**唯一代价是其他端可见性延迟**，换取配额消耗下降 ~150 倍。

## 5. 后果

**正面**
- 默认档远离一切限流线（60× 余量），几乎不会触发 ADR 之外的 failover；
- 配额消耗可预算化（QuotaManager 按档位预算）；
- 移动端省电省流量（无轮询）。

**负面 / 已知代价**
- 多端可见性延迟默认 10 分钟（可调档或手动 `sync()` 缓解）；
- 秒级实时需求必须外挂事件总线，GitLite 本体不提供；
- 「窗口内退出」依赖 flushOnExit 钩子，宿主壳必须正确接入生命周期事件（Electron `before-quit`、Capacitor `appStateChange` 等，adapter 层负责）。

# ADR-002 · 格式宪法（Format Constitution）

**标题**：仓库文件/目录结构标准锚定开放标准，additive-only 演进，formatVersion 门禁，v0.3 冻结 1.0.0

**状态**：已采纳（schema 文件格式已按此重构，见 [03-data-model.md](./03-data-model.md) §二、§十一）

## 1. 背景

GitLite 的「数据库」物理上就是远端仓库里的文件与目录结构。软件必然多次迭代（v0.1 → v1.0+），且**多客户端版本长期共存**（同一用户多台设备装着不同版本的 app）。这带来一个其他嵌入式数据库没有的问题：

> **格式 breaking 变更 = 全部存量用户数据库需要迁移或重置。**

用户明确要求：「标准需要尽快完善定型，尽量不修改，不然容易导致数据库丢弃、重置」。

### 约束条件

1. 格式一旦发布，兼容性承诺周期以**年**计；
2. 迁移要跑在 Git API 上——大规模迁移本身就是配额灾难（迁移一个 10k 文档库 ≈ 数千次 API 调用）；
3. 旧版客户端**无法被强制升级**（用户设备上的 app 版本不受控）；
4. 格式要能被第三方工具理解（备份、审计、迁移脚本）。

## 2. 备选方案对比

| 维度 | A. 自定义格式自由演进 | B. 自定义格式 + 迁移工具 | **C. 开放标准锚定 + additive-only + 门禁（采纳）** | D. 直接复用现有方案（Decap/Tina 文件布局） |
|---|---|---|---|---|
| 前期设计自由度 | 最大 | 大 | 中（受标准约束） | 小（受制于人） |
| breaking 对用户影响 | 每次全量 | 每次需跑迁移（吃配额、可能失败） | **仅 major（预期极少次）** | 取决于上游 |
| 旧客户端兼容 | 不可控 | 不可控（打不开新格式） | **未知容忍规则保证不损坏** | 不可控 |
| 第三方工具复用 | 无 | 无 | **JSON Schema 生态全量可用** | 部分 |
| 迁移工具成本 | — | 每次变更都要付 | 仅 major 付一次 | — |
| 测试基建投入 | 低 | 中 | **高（黄金仓库 CI）** | 低 |
| 与「不重置」目标的契合 | 差 | 中 | **好** | 差 |

### 各方案否决/采纳理由

**A. 自定义格式自由演进 — 否决**
与「不重置」目标直接冲突。自由度换来的迭代速度会在第一次 breaking 时以用户信任为代价偿还。

**B. 自定义格式 + 每次变更配迁移工具 — 否决**
三个致命伤：① 迁移跑在 Git API 上，大规模迁移 = 配额灾难；② 迁移失败的回滚在分布式多端环境下极复杂；③ 旧客户端仍然打不开新格式仓库，迁移没解决版本共存问题。

**C. 开放标准锚定 + additive-only + 门禁 — 采纳**
把「不变」外包给最稳定的标准化组织：字段校验语义交给 JSON Schema 委员会（数十年承诺），ID 交给 ULID 冻结 spec，版本号交给 SemVer。自造面收缩到目录布局 + vendor 扩展，而这两块用 additive-only + 未知容忍规则锁死演进方式。

**D. 直接复用 Decap/Tina 布局 — 否决**
它们面向「内容编辑」而非「数据存储」，无事务/索引/分片概念；且其格式演进不受 GitLite 控制，等于把格式主权交给不受本社区治理的上游。

## 3. 最终决策

### 3.1 锚定的开放标准（能借的绝不自造）

| GitLite 结构 | 锚定标准 | 稳定性来源 |
|---|---|---|
| 底层存储模型 | Git 对象模型（blob/tree/commit/ref） | Git 15+ 年向后兼容 |
| 文档与分片文件 | JSON（RFC 8259）、JSONL | 通用基础标准 |
| **schema 字段校验** | **JSON Schema Draft 2020-12**（子集） | 标准委员会维护 |
| 主键 ID | ULID 官方 spec | 规范冻结 |
| 时间戳 | ISO 8601（UTC） | 冻结 |
| 格式版本号 | SemVer 2.0.0 | 冻结 |
| MD collection | YAML frontmatter | 生态通用惯例 |
| 自定义关键字 | 一律 `x-gitlite-*` 前缀 | 仿 OpenAPI `x-` 惯例 |

自造面收缩到两处：**目录布局约定**（[03 §一](./03-data-model.md)）+ **`x-gitlite-*` 扩展关键字**。

### 3.2 schema 文件格式（已按此重构）

标准 JSON Schema 关键字原样使用（`type` / `enum` / `pattern` / `format` / `maxLength` / `minimum` / `maximum` / `items` / `properties` / `required` 数组 / `default`）；GitLite 特有语义全部进 vendor 命名空间（`x-gitlite-unique` / `x-gitlite-indexed` / `x-gitlite-encrypted` / `x-gitlite-immutable` / `x-gitlite-ref` / `x-gitlite-relations` / `x-gitlite-indexes`）；collection 级配置集中在 `gitliteDescriptor` 块。

### 3.3 formatVersion 版本门禁

`gitlite.config.jsonc` 头字段（对标 SQLite 文件头 read/write version 哲学）：

| 情形 | 行为 |
|---|---|
| repo.major == client.major | 正常打开（minor/patch 差异必须兼容） |
| repo.major < client.major | 正常打开（新客户端向后兼容） |
| repo.major > client.major | **拒绝打开**，提示升级（防旧客户端写坏新格式） |

### 3.4 演进规则：additive-only

1. **允许**（minor 升级）：新增 `_` 系统目录/文件、文档新增可选元字段、新增 `x-gitlite-*` 关键字、索引文件新增可选字段。
2. **禁止**：改已有路径/命名、改字段语义、删除系统文件、改 `_rev` 算法、改 JSONL 行结构。
3. **未知容忍（前向兼容核心）**：客户端遇到不认识的 `_` 目录/文件/schema 关键字/文档元字段——读路径忽略、写路径**原样保留**。此规则保证旧客户端永不损坏新格式仓库。
4. **major 升级**：仅绝对必要时，必须伴随官方迁移工具且可回滚。

### 3.5 冻结与验证机制

| 机制 | 说明 |
|---|---|
| 早期冻结 | v0.1–v0.2 标 `0.x.0`（实验期，允许重置，UI 明示）；**v0.3 冻结 `1.0.0`** |
| 黄金仓库测试集 | CI 维护各版本快照仓库，每版必须通过「读全部历史黄金仓库 + 写回等价」测试 |
| 双客户端互操作 | 最新版 × 历史版（N-2 起）交叉读写测试 |
| 格式变更 RFC | 提案 → 影响评估 → 迁移方案 → 冻结 |

### 3.6 进入冻结范围的核心结构（v1.0.0 清单）

- 分支命名：`gitlite/<database>`、`gitlite/tx/<txId>`
- 根级：`gitlite.config.jsonc`、`_schema/`、`_indexes/`、`_migrations/`、`_meta/`
- collection 布局：L0 `<c>.jsonl` / L1 `<c>/<id>.json` / L2 `<c>/shard-NNNN.jsonl`
- 文档元字段：`_id`（ULID）、`_rev`（SHA-1 前 12 位）、`_schema`、`createdAt`/`updatedAt`
- schema 格式：JSON Schema 2020-12 子集 + `x-gitlite-*`

## 4. 后果

**正面**
- 用户数据库「发布即长期有效」，兑现「不丢弃、不重置」承诺；
- JSON Schema 生态工具（校验器、IDE 补全、文档生成）零成本复用；
- 格式变更成本前置且可控（RFC + 测试基建），不会意外破产；
- 第三方可安全编写针对 GitLite 仓库的备份/审计工具。

**负面 / 已知代价**
- 设计自由度永久受限：任何语义改动只能走 major + 迁移工具，团队必须克制「顺手优化格式」的冲动；
- 标准子集的取舍需要一次性做对（v0.3 前是唯一窗口）；
- 黄金仓库 CI + 双客户端互操作测试是持续投入；
- JSON Schema 部分关键字（如 `$ref` 远程引用）不在子集内，需在文档中显式声明不支持，避免用户误用。

## 5. 与 ADR-001 的关联

两项决策共同服务于同一产品底线——**「配额不踩雷、数据不丢失」**：

- ADR-001 保证运行时不被限流打断（频率侧）；
- ADR-002 保证存量的长期有效性（格式侧）；
- 二者叠加，用户数据在「分钟级新鲜度」与「多年期可读」之间取得工程平衡。
